## Пример. Совместное использование сигналов и каналов - "пинг-понг"

```c
#include <signal.h>
#include <sys/types.h>
#include <sys/wait.h>
#include <unistd.h>
#include <stdlib.h>
#include <stdio.h>

#define MAX_CNT 100

/*Целевой пид, cnt - мячик*/
int target_pid, cnt; 
int fd[2]; //файловые дескрипторы для именовго канала
int status; 

/*
Будем посылать сигнал, что кинули мячик
s - seek_user_1
*/
void SigHndlr (int s)   
{	
	if (cnt < MAX_CNT) 
	{
		read(fd[0], &cnt, sizeof(int));
		printf("%d \n", cnt);
		cnt++;
		write(fd[1], &cnt, sizeof(int));
		kill(target_pid, SIGUSR1);
	} else 
	if (target_pid == getppid()) /* процесс – сын*/
	{
		printf("Child is going to	be terminated\n");
		close(fd[1]);
		close(fd[0]);
		exit(0);
	} else /* процесс – родитель */
		/*Дополнительная передача,
		чтобы первым завершался сын*/
		kill(target_pid, SIGUSR1);
}

int main(int argc, char **argv)
{  
	pipe(fd); //сделали неименованный канал
	signal(SIGUSR1, SigHndlr);
	cnt = 0;

	/*сформировали сыновий процесс*/
	if (target_pid = fork()) { /* процесс – родитель*/
		/*записали в канал мячик*/
		write(fd[1], &cnt, sizeof(int));  
		
		/*запустили бесконечный цикл
		Когда завершится сыновый процесс, 
		тогда выйдем из цикла*/
		while(wait(&status)== -1); 
		
		printf("Parent is going to be terminated\n");
		
		close(fd[1]); 
		close(fd[0]);
		
		return 0;
	} else { /* процесс – сын */
		/*считали счётчик из канала*/		
		read(fd[0], &cnt, sizeof(int)); /* старт синхр*/
		
		/*Определяем сыновий пид для целевого процесса*/
		target_pid = getppid();
  		
  		/*возвращаем мячик в канал и передаём 
  		целевому пиду сигнал*/
  		write(fd[1], &cnt, sizeof(int));
		kill(target_pid, SIGUSR1);
		for(;;);
	}
} 
```

# Взаимодействие "главный подчинённый"
Есть главный, у окторого большой набор взаимодействий

```c
#include <sys/ptrace.h>

int ptrace(int cmd, int pid, int addr, int data);
```
- *cmd* – код выполняемой команды:
	- <u>группа команд чтения</u> (сегмент кода, сегмент данных, контекст процесса)
		- Из контекста процесса можем читать регистры
	- <u>группа команд записи</u> (сегмент кода, сегмант данных, контекст процесса)
		- подчинённый процесс приостановлен
	- <u>группа команд управления</u> (продолжить выполнение, продолжить выполнение с заданного адреса, включить "шаговый режим", завершить процесс, разрешить трассироваку)
		- команды, которые может исполнять главный процесс
		- продолжить выполнение с точки остановы подчинённого процесса
		- Запустить подчинённый процесс с заданого адреса
		- Процесс должен разрешить себя тресировать
- *pid* – идентификатор процесса-потомка
- *addr* – некоторый адрес в адресном пространстве процесса-потомка
- *data* – слово информации.

## Схема установки контрольной точки по адресу A<sub>BrPnt</sub>
### Установка контрольной точки
*Статус оотлаживаемого процесса (ОП)* **ВЫПОЛНЕНИЕ**
- послать `Sigtrap`
- ждём остановку ОП + анализ точки остановки (статут ОП **ОЖИДАНИЕ**)
- чтение в адресном пространстве ОП, сохранение (N<sub>BrPnt</sub> <A<sub>BrPnt</sub>>)
- запись BrPnt в A<sub>BrPnt</sub>
- продолжить с точки останова
### Приход в контрольную точку
*Статус (ОП)* **ВЫПОЛНЕНИЕ**
- ждём остановки ОП, остановка (статус ОП **ОЖИДАНИЕ**)
- чтение адрес остановы. Из wait получаем причину остановы
- проверяем, совпадает ли причина с адресом остановки - т.е. пришли в контрольную точку
- запускаем дальнейший процесс с адреса контрольной точки

`контрольная точка может быть многократной`
В этом случае после того, как мы пришли в многократную к т. мы когда хотим запустить программу, мы делаем
1. Восстанавливаем содержимое адреса, которое там было
2. Включаем шаговый режим
3. Передаём управление на адрес к т
4. Система приостановит процесс на следующей команде
5. Восстанавливаем к т по адресу
6. И запускаем процесс без шагового режима

# Система межпроцессного взаимодействия IPC
- В рамках локальной машины
- Разделяемые ресурсы вне процессов их использующих

Система IPC предлагает использовать разделяемые ресурсы трёх типов
1. Очередь сообщений
2. Разделяемая память - общая оперативная память
3. Массив семафоров - не семафоры Дейкстра, это другое
	- Могут подключаться произвольные, не обязательно родственные процессы

- **Семафорные операции**: атомарные, могут в зависиомсти от семафора или операции испольняться или блокировать и потом доисполняться. Операции можно выполнять одновременно с несколькими семафорами из массивов семафоров

## Общая концепция
### `ftok`

- Для идентификации разделяемых ресурсов
- Генерация уникальных ключей
- Чтобы производить развод генерации имём, есть функция `ftok`
```c
#include <sys/types.h>
#include <sys/ipc.h>
key_t ftok (char * filename, char proj) 
```
`Параметры`:
- `filename` - строка, содержащая имя файла
	- Генерим по имени и **характеристикам** файла
- `proj` - добавочный символ

### `get`

- 
Для всех ресурсов есть вызовы группы `get`
`<ResName> get(key, ..., flags)` - создание/подключение

- **Флаги** - битовая шкала, с конкретным флагом связан конкретный бит. Комбинация через операцию `или`

Возвращает файловый дескриптор.
- `IPC_PRIVATE` (доступ только породившему процессу)

- Флаги создания/подлючения:
	- `IPC_CREAT` (**создать новый** или **подключиться к существующему**)
	- `IPC_EXCL` (+ `IPC_CREAT` создание только нового `IPC_EXCL | IPC_CREATE` )
	- `IPC_RMID` - удалить ресурс
		- Может это сделать процесс, у которого эффект идентифактор совпадает с идентификатором, кто создал этот ресурс, или имеет `root` права

# Взаимодействие процессов: **сокеты**
- средство, которое повзволяте организовывать взаимодействие как в рамках локальной машины, так и в рамках локальной сети или Интернета

![](_resources/Pasted%20image%2020251106100944.png)
- Какой коммуникационый домен будет использоваться после создания, он определяет способ адресации взаимодействующих процессов. Определяет формат информации об адреса
	- `AF_INET`
	- `AF_UNIX`

- Каждый из сокетов может иметь свой тип:
	- **тип виртуальный канал**
		- Предполагает логическое соединение между взаимодействующими сокетами и организация порядка приёма и отправка пакетов/сообщений
	- **датаграмма**
		- Отправка отдельный пакетов - сообщений, в котором нет  установления соединения, в котором не гарантируется соблюдения порядка отправки и приёмки сообщений, не гарантируется доставка их сообщений

- Сокет характеризуется тем протоколом, который будет использован для передачи сообщений. Конкретные протоколы имеют смысл для коммуникационного домена - Интернет. Для UNIX используются свои протоколы

- Для создания сокета есть вызов `socket`
```c
int socket(int domain, int type, int protocol);
```
Параметры:
- `domain` - коммуникационный домен
	- `AF_UNIX`
	- `AF_INET`
- `type` - тип сокета:
	- `SOCK_STREAM`
	- `SOCK_DGRAM`
- `protocol` - протокол:
	- 0

- Для сокета типа датаграмма может использоваться и `udp` и `tcp`
- Для виртуального канала может использоваться только протокол `tcp`

### Предварительное соединение
![](_resources/Pasted%20image%2020251106105352.png)
**Сервер:**
- Мы создали сокет
- Для сервера принципиально, чтобы было имя (пример с Игорем Валерьевичем)
- Происходит **связывание** - сокету даётся имя

- Сервер обращается к вызову `listen` - открывает сокет на приём запросов на соединение. Вызов `listen` обговаривает, что заданный сокет может принимать запрос на соедение и обговаривает параметры очереди. Он определяет размер очереди, но `как-то по особенному`
- Если пришло заявление на соединение до `listen`, то процесс-клиент получит **отказ**

- `accept` - обработка запроса
- блокируемся, если ничего нет
- Если есть запрос, то выбирает один из них и происходит следующее:
	- По результату работы `accept` создаётся ещё один socket, связанный с сокетом клиента, с запросом которого работал `accept`
- Взаимодействовать с клиентов будет сокет, который создат `accept`, кторый связан с сокетом клиента

- Есть блокирующие вызовы `send` и `recv`. Происходит общение сервера и клиента

- Завершение
**Клиент:**
- Создаёт свой сокет
- Может именовать / может не именовать свой сокет через `bind`
- Он обращается к серверу
- Еслии сервер не выполнил `listen`,  то получаем отказ
- Если выполнил `listen`, то происходит блокировка на ождиниае вопроса на соединение

### Пример №1
- Есть модель клиент - сервер
- Клиент формирует текстовую строку со своим PID, которую отправляет на сервер и дожидается получение ответа от сервера

- Цель: разработать программную реализацию Клиент/Сервера, взаимодействующего в пространстве домена AF_INET. 
- Клиент: 
	- создает свой сокет и через него запрашивает соединение к серверу по заданному адресу;
	- формирует текстовую строку с номером PID’а своего процесса, которую отправляет на сервер; 
	- ожидается получения информации в виде текстовой строки от Сервера, выводит ее на стандартное устройство вывода. Далее закрытие сокета.
- Сервер:
	- создает свой основной сокет и открывает основной сервер на прослушивание. 
	- подтверждает запросы на соединение с каждым Клиентом. 
	- для каждого соединения Сервер формирует отдельный процесс в котором будет осуществляться взаимодействие с Клиентом. 

- Для обеспечения возможности самостоятельного запуска демонстрационного примера сетевого взаимодействия в рамках одной локальной ВС, в качестве IP адреса Сервера может использоваться зарезервированный IP адрес 127.0.0.1 – означает, что к серверу могут обращаться только клиенты, находящие в рамках одной и той же ВС, что Сервер.
- При запуске клиент-сервера в рамках реальной сети, потребуется использование реального IP адреса компьютера (заметим, что у одного компьютера может быть несколько IP адресов – к примеру, у выполняющего функцию шлюза.

Используемые библиотечные функции:
- `inet_addr (…)` – преобразует IP адрес из строки в число в сетевом представлении;
- `htons (…)` – преобразует 2-байтное число в число в сетевом представлении;
- `htonl (…)` – преобразует 4-байтное число в число в сетевом п редставлении;
- `inet_ntoa (…)` – преобразует IP адрес из сетевого представления в строку.
- `INADDR_ANY` –предопределенная константа, использование которой обеспечивает «привязку» ко всем IP адресам данного сервера, включая 127.0.0.1 .
